--------------------------------------------------------------------------------
0. WITHDRAWN — the mechanism this transcript first claimed, and its refutation
--------------------------------------------------------------------------------
An earlier draft of this file claimed the inflating pressure was co-tenancy
INSIDE the vitest worker process: "work in the SAME PROCESS ... belonging to the
other test files that worker is chewing through". THAT IS FALSE, and it is false
for a reason that is checkable in one line.

    $ grep -n "pool" vitest.config.ts
    (no output)

`vitest.config.ts` sets no `pool`. Vitest 4.1.10 resolves the default at
`node_modules/vitest/dist/chunks/coverage.DM_a_rWm.js:180`:

    resolved.pool ??= "forks";

and `isolate` defaults to `true`
(`node_modules/vitest/dist/chunks/defaults.9aQKnqFk.js:47`). **Every test file
runs in its own forked child process.** `process.resourceUsage()` is
`getrusage(RUSAGE_SELF)`, which cannot see another process. So no other test
file's module graph, GC or coverage work can enter this measurement, and the
withdrawn sentence described something that cannot happen.

The second withdrawn claim, refuted by measurement in §3: "external host load
barely moves this metric at all." It does move it. The probe behind that
sentence used 8 busy loops on a 16-core host — the process was never starved, so
the probe could not have shown anything.

The third withdrawn claim, refuted by reading: the arm's scheduler "fires ZERO
times inside the window". `heartbeat-scheduler.ts:45` is

    tick(); // one immediate sample so callers have data before the first interval elapses

inside `start()`, which `idle-budget.integration.test.ts:26` calls. It fires
exactly ONCE — the immediate tick — and never again, because the 5 s interval
does not elapse inside a 1.5 s window. "Once, not zero" is a small correction
with a real consequence: the subject is not entirely absent from its own
measurement.

1. WHAT THE NUMBER IS
--------------------------------------------------------------------------------
    idle-budget.integration.test.ts
    :15  const CPU_BUDGET_FRACTION = 0.01;      // <1% of one core
    :16  const SUSTAINED_WINDOW_MS = 1_500;
    :26    scheduler.start();                   // fires once, immediately
    :28    await new Promise((resolve) => setTimeout(resolve, SUSTAINED_WINDOW_MS));
    :46    expect(cpuFraction).toBeLessThan(CPU_BUDGET_FRACTION);

    resource-probe.ts:37-45
      cpuDelta  = (userCPUTime + systemCPUTime) delta     // getrusage(RUSAGE_SELF)
      wallDelta = Date.now() delta
      fraction  = cpuDelta / wallDelta

So: **all CPU consumed by this forked worker process — every thread of it,
including V8's GC and compiler threads and libuv's pool — over 1500 ms of wall
clock, while the subject under test does almost nothing.** What is in the
numerator is the worker's own overhead: v8 coverage collection, GC, the module
graph of the one file it is running, and whatever the OS scheduler charges it.

WHERE THE THRESHOLD CAME FROM. Not from a measurement:

    $ git log -S "CPU_BUDGET_FRACTION = 0.01" --oneline -- \
          packages/supervisor/src/idle-budget/idle-budget.integration.test.ts
    42c9afe feat: phase 05 supervisor daemon and UDS control plane

One commit — the phase's own implementation commit. The constant was
TRANSCRIBED from the roadmap criterion's words ("<1% of one core"), which is the
right thing to have done for a SPEC number, and it means the figure has never
been calibrated against the distribution of the instrument that checks it.

⚠️ And the earlier draft's "what is not stated anywhere" was wrong too:
`roadmap/05-supervisor-daemon.md:122` states the measured CI figure explicitly,
