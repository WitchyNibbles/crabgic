1. THE SEAM DECISION, AND THE CONSUMER CENSUS BEHIND IT
--------------------------------------------------------------------------------

A tenant is decidable inside the pipeline: `RemoteMutationPlan.tenant` is a
required field. A FOLDER IS NOT ON THE PLAN AT ALL —

$ sed -n '/RemoteMutationPlanSchema = /,/\.strict()/p' \
      packages/contracts/src/contracts/remote-mutation-plan.ts
  → 14 members; none names a folder; the object is `.strict()`, and the desired
    state is present only as `desiredStateHash` + `redactedDiff`.

So the pipeline cannot decide this alone. Three seams were possible:

  (a) add a folder field to `RemoteMutationPlan`
      REJECTED. `.strict()` + a phase-02-owned contract ⇒ a coordinated change
      across 02/16/18/20 and the interface ledger, and every plan builder in
      every connector would have to fill a field only Grafana can populate.
  (b) check inside `GatewayHttpClient.request()`
      REJECTED for the same reason PR #100 rejected it for tenants: read
      requests carry pseudo-tenants used purely as concurrency keys, and the
      request layer has no notion of the plan at all.
  (c) a PROVIDER HOOK on the handler set, consulted by `executeMutationPlan`
      CHOSEN. It mirrors the `serializationTarget` seam that already exists two
      members above it: same optional shape, same purity requirement, same
      forwarding path through the apply-tool bridge.

CONSUMER CENSUS for (c) — by consumer, not by type name (a type-name grep misses
inferred object literals). Census route: every construction of
`MutationPipelineDeps`, found via its `tenantAllowlist` member, then filtered:

  production (1)  packages/gateway/src/mcp/native-tools/mutation-apply-tool.ts
  re-entrant (1)  packages/connectors-grafana/src/mutation/apply-with-rebase.ts
                  — takes deps from its caller, so it is covered by the same
                    single check rather than needing a second one
  tests/e2e (16 files carrying `folderAllowlist: undefined` — 12 `.ts`
            suites/harnesses and 4 `.mjs` crash-harness fixtures)

Exactly ONE production site can see the real `ExternalConnection`, and it is the
one that already hands over `tenantAllowlist`. That is where the wiring went.

WHO CAN ANSWER THE HOOK — census over the closed 7-kind Grafana list
(packages/connectors-grafana/src/resource-kinds.ts), each row read from that
kind's own `CANONICAL_FIELD_KEYS` rather than guessed:

  kind                   | field naming a folder      | ruling
  -----------------------|----------------------------|------------------
  folder                 | (the resource IS a folder) | folders: [own uid]
  dashboard              | folderUid                  | folders: [it]; "" ⇒ outside-folders
  alert-rule             | folderUID  (capital UID)   | folders: [it]; absent ⇒ unknown
  annotation             | dashboardUID only          | unknown (transitive; needs a read)
  contact-point          | —                          | outside-folders (org-level)
  mute-timing            | —                          | outside-folders (org-level)
  notification-template  | —                          | outside-folders (org-level)

Jira (18/19) has no folder in its model and registers no hook at all.

That census is why the answer type has THREE members, not two:
`{folders}` / `{outside-folders}` / `{unknown}`. Collapsing the last two would
make a lost plan-payload entry indistinguishable from a genuine root-level write.

2. THE RULING THAT FILLS THE SPEC SILENCE
--------------------------------------------------------------------------------

roadmap/16 names "folder allowlists" and says nothing about a provider that has
no folder concept. Two readings were available:

  ADMIT when unattributable — the field then binds only providers that opted in,
    with nothing telling an operator which. That is the same trusted-and-inert
    control shape the defect record is about, rebuilt one level up.
  REFUSE when unattributable — chosen.

Visible consequence, written into the code and the published `.describe()` so it
is not later rediscovered as a bug: setting `folderAllowlist` on a JIRA
connection refuses every Jira mutation on it, loudly and with a typed
`policy_blocked` reason.

Probe I below implements the REJECTED reading and shows exactly which assertions
separate the two, so the ruling is measured rather than argued.

5. SCOPE — what this does NOT bind
--------------------------------------------------------------------------------

Stated here, in the published `.describe()`, in the schema JSON, and beside
`refuseOutOfAllowlistFolder` itself, because an oversold control is how one ends
up trusted and inert:

  - MUTATIONS ONLY. Reads are not folder-checked, for the same reason they are
    not tenant-checked: read requests carry pseudo-tenants used purely as
    `WriteSerializer` concurrency keys.
  - DECLARED PLACEMENT, NOT ACTUAL. It binds the folder the provider derives
    from the plan's own stored payload. Nothing here verifies where the resource
    actually lives on the remote; a dashboard moved server-side still reports its
    plan's folder.
  - It is therefore NOT "writes outside these folders are impossible". It is
    "an operator can bound which folder a write may claim to land in."
  - `annotation` is `unknown` by construction, so on a folder-scoped connection
    Grafana annotations are refused rather than placed. That is deliberate and
    pinned; making it precise needs a remote read this hook may not perform.

Nothing in this transcript evidences behaviour against a real Grafana or Jira.
Every leg is a fake transport with a real journal.
