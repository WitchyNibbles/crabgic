READ THAT OUTPUT CAREFULLY — it establishes three things:

  (a) FILE ORDER IS NOT INCLUDE ORDER. `plugin-load.live.test.ts` is line 1 of the run;
      `plugin-negative-space.live.test.ts` is 16th of 17. vitest does not order files by which
      include pattern matched them, so the plan's "the expensive files run first" is wrong in
      both directions — the two plugin files are scattered, not appended.

  (b) THE ORDER DOES NOT MATTER, WHICH IS THE REAL POINT. `npm run test:live` is
      `vitest run --config vitest.live.config.ts` with NO `--bail`. All 17 files ran here
      (`Test Files  17 failed (17)`). So on CI a plugin ENOENT does NOT stop the engine-claude
      files: every one of them still runs, still authenticates, and still spends. The full
      ~60-90-invocation cost is paid whether the plugin lane fails first, last, or in the middle.
      The hazard therefore survives the correction — the plan's conclusion was right for a
      reason the plan got wrong.

  (c) THE FAIL-CLOSED GATE IS REAL, and is why this accident cost nothing. Every engine-claude
      file reports `N tests | N skipped` with a failed suite, and the four plugin cases report
      `× ... 0-4ms` — a `LiveEnvNotEnabledError` from `assertLiveEnabled`, thrown in `beforeAll`
      before any engine call. The harness's own message states the intent:
      "CRABGIC_LIVE is not set to '1' — the @live conformance suite refuses to run and MUST fail
      red, never skip silently (the engine-live CI job must go red, not vacuously green,
      without it)."
      On a real CI dispatch `CRABGIC_LIVE=1` IS set (engine-live.yml:50), so this gate would not
      fire and nothing would stand between the run and the spend.
