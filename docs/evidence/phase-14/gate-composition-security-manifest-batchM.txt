9. WHAT THIS BATCH DELIBERATELY DID **NOT** REGISTER, AND THE MEASURED REASON
--------------------------------------------------------------------------------

Stated so nobody reads this as "the gate registry is now complete". It is not.
`registry.list("performance")`, `list("tdd")`, `list("coverage")`,
`list("flake")` and `list("engine-conformance")` are all still `[]`, and the
suite asserts it.

15's PERFORMANCE GATE — not registered. `fireAll` fires every registered gate for
every run (packages/gates/src/registry.ts:84-95), so a perf handler without a
real measurement backend either throws (the daemon can never publish, in any
deployment) or fabricates measurements (forbidden). The backend is missing in
four independent places:
  1. `GateContext` (packages/gates/src/types.ts) carries no `baseObjectId`, so
     the A side of the A/B benchmark is not reachable from the firing context —
     a gates-owned contract change.
  2. The twin-worktree runner must be built on the scheduler's `dispatchAttempt`,
     whose outcome does not expose `worktreePath` — the documented CARRY-FORWARD
     at packages/perf/src/runner/twin-worktree-runner.ts:56-65.
  3. `benchmarkCommand` comes from `ProjectProfile.ecosystems[].benchmarkCommand`
     and no production code composes a `ProjectProfile` anywhere.
  4. The methodology floor demands >=10 measured plus warmup reps per side, i.e.
     22+ sequential stack commands per run — and stack commands are exactly what
     roadmap/14 WI6's `TaskPacket`/worker-sandbox dispatch is a precondition for
     (packages/cli/src/daemon/post-completion-pipeline.ts:49-60). That is sandbox
     posture, not preference.
Also: docs/interface-ledger.md:1574 and :1683 record that
`createPerformanceGateHandler` has no production caller, so registering it is a
coordinated ledger amendment, not a one-line change. This batch keeps both lines
true.

14's OWN TRANCHE — not registered, same shape. The coverage gates need report
files nothing composes; the scanner gates need digest-pinned binaries from 12's
capability store, which the daemon does not compose; and
`createEngineConformanceGate` needs a journaled green `engine-live` record while
`engine-live.yml` has never run at all — registering it today would fail every
run for want of evidence that is itself owner-gated.

The six security fixtures are the SAFE subset precisely because none of them
executes a stack command: pure in-memory checks of the installed build's own
primitives (a refused `issue.delete`; the absence of forged operations on the
Grafana adapter surface; a tenant-boundary scenario over an in-memory fake
transport whose `send` returns a canned 200; three redaction round-trips). No
subprocess, no network, no filesystem, no engine — millisecond-scale and
environment-independent, the same defensibility class as the seal gate.
