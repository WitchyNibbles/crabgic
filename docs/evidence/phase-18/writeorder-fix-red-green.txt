  2026-08-02 criteria-closeout pass; named in prose, deliberately not cited —
  docs/evidence/criteria-closeout/ is the claim-space).

  The defect, measured: two writes of DIFFERENT KINDS to the SAME issue, built by
  the real resource client and applied through the real `executeMutationPlan`,
  ran concurrently (`maxInFlight = 2`) because serialization keys on
  `plan.canonicalTarget` and this connector mints four distinct targets for one
  issue (`issue:K`, `issue:K:comment`, `issue:K:worklog`, `issue:K:attachment`).

  The fix does NOT collapse `canonicalTarget` (it is identity — both apply
  clients parse a `commentId` back out of it). It adds an optional
  `serializationTarget` hook on `MutationApplyClient` /
  `MutationPipelineHandlers`, defaulting to `canonicalTarget`, consumed at the
  pipeline's single `httpClient.request` call site and forwarded by
  `mutation-apply-tool.ts`. Both Jira apply clients (Cloud + Data Center) fold
  every issue-scoped shape onto `issue:<key>` via one shared derivation.

NOT A WALL-CLOCK TEST
  Overlap is detected by a deferred-promise barrier that releases the moment N
  requests are simultaneously in flight. The bounded fallback timer is reachable
  ONLY by the first request of a correctly-serialized batch (in which no sibling
  can ever arrive to release the barrier), so a loaded machine LENGTHENS the hold
  rather than shortening it — which makes the `=== 2` controls more reliable
  under load, not less. No test asserts a duration.

  `engine-live`, no `jira-datacenter-smoke`. Every request is served by an
  injected `sendRequest`; every journal is a real temp dir.
