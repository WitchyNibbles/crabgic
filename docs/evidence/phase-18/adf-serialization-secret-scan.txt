0. The gap
----------
`assertSafeAdfDocument`'s secret scan consumed only `extractPlainText`'s output,
i.e. `node.text`. Two shapes bypassed it and reached the outbound payload:

  (a) a link mark's `attrs.href` — `validateAdfSafeSubset` checks the href
      SCHEME only, so a well-formed `https:` URL with a secret in its query
      string is structurally valid and was never content-scanned;
  (b) an unknown extra member on a node — `validateAdfSafeSubset` walks only
      `type`/`marks`/`content`, so `{type:"text", text:"hi", note:"<key>"}` is
      structurally invisible, yet Cloud's apply client spreads the payload
      record wholesale into the request body.

Cloud: the outbound body IS `JSON.stringify` of the guard's document.
Data Center: the href is emitted literally inside the wiki `[text|href]`
construct by `datacenter/wiki-markup-render-profile.ts`.

PROBE A shows the new check is load-bearing for all six assertions, and that the
RED in section 3 is reproducible from a committed tree.

PROBE B is the one that matters for scope. It replaces the serialization scan
with an href-only walk that collects `mark.attrs.href` and scans just those
strings. Under it the two href tests and the two apply-boundary tests go GREEN —
so an href-only fix looks equivalent if you only run those — while the
unknown-member test STAYS RED. That is the measured proof that the
unknown-member test is a scope tripwire rather than a restatement of the href
test, and it is why the check scans the serialization instead of an enumerated
attribute list. Weakening or deleting that test to get green would silently
reopen the smuggling path.

(The fail-closed and provider-attribution assertions also stay red under B,
because the href-only walk never serializes and so cannot fail closed.)

7. Residual, pinned rather than described
------------------------------------------
A circular reference routed through a member the recursive walkers DO descend
into (`content`) exhausts the stack inside `validateAdfSafeSubset` /
`extractPlainText` and surfaces as a `RangeError`, not a `ConnectorError`. That
is pre-existing behaviour of those shared walkers, unchanged by this work and
outside its one-file scope. It is now encoded as an assertion in
adf-guard.test.ts so it announces itself if anyone alters those walkers, instead
of drifting silently in prose.

Cycles through members the walkers skip (e.g. `attrs`) DO reach the new
serialization step and are mapped to a typed `policy_blocked` — that is the case
the fail-closed test covers, and its `expect(() => JSON.stringify(doc)).toThrow(TypeError)`
line proves the hazard is real rather than hypothetical.


8. Accepted trade-off, stated
------------------------------
A legitimate URL that genuinely contains an `AKIA`+16 shape, a PEM header, or
`aws_secret_access_key=` in its query string will now be blocked. That is the
correct behaviour — such a URL is indistinguishable from exfiltration — and the
measured incidence across the repo's real URL corpus is 0 (section 1).
