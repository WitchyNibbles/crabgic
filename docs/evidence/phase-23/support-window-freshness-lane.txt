--------------------------------------------------------------------------------
1. THE PROBLEM — a gate with no per-push caller and a hard date behind it
--------------------------------------------------------------------------------
`e2e/attestation`'s `checkVersionSupportWindows` refuses a release once the
committed record is more than `DEFAULT_MAX_RECORD_AGE_DAYS` (30) old at the cut,
or once a vendor window has closed.

It has NO production caller. Its only invocation anywhere is inside
`e2e/attestation`'s own suite, which runs solely under
`npm run test:e2e:release-evidence` — the step `.github/workflows/publish.yml`
blocks on at a `v*` tag. `e2e/attestation` is not a `vitest.config.ts` project,
so nothing per-push ran it.

Every record carried `confirmedOn: 2026-07-25`. 2026-07-25 + 31 days =
2026-08-25 ⇒ from 2026-08-25 no release could be cut, and the failure would have
landed inside a tag-triggered publish, with nothing having said a word.

--------------------------------------------------------------------------------
1b. ⚖️ THE ARM SPLIT — owner ruling 2026-08-07, correcting this lane's own first
    version
--------------------------------------------------------------------------------
The first version of this check FAILED per-push on BOTH a stale probe stamp and
an expired vendor window, in a REQUIRED `meta-checks` step. The undisclosed
consequence: from the 31st day after each probe run, EVERY PULL REQUEST IN THE
REPOSITORY would have gone red until a human ran the probe and committed. That
is an escalation from "cannot cut a release" to "cannot merge anything", for
work with no connection to releasing. The condition was stated in the PR; the
consequence was not.

The two things measured here carry different risks and must not share a blast
radius:

  ARM A — STALE PROBE STAMP. Risk: "we would be SHIPPING on evidence nobody
          re-checked." That is a release-time risk and nothing else.
          ⇒ WARNS per-push, from T-21 and thereafter, however stale.
          ⇒ FAILS at a release cut, where it already did and still does —
            `e2e/attestation`'s `checkVersionSupportWindows`, which
            `publish.yml` blocks on at a `v*` tag.

  ARM B — EXPIRED VENDOR WINDOW. Risk: this repository pins a version the
          vendor has stopped supporting. True right now, for everyone.
          ⇒ FAILS everywhere, per-push included.

Malformed records (future-dated, missing target, versioned target with no
support-end date) and auto-renewal offenders FAIL everywhere too: they are
integrity errors, not clocks.

⚠️ THE RELEASE-TIME HALF IS NOT A PROMISE IN A COMMENT. Asserting it by
grepping `versionSupportWindows.ts` for a `fail` branch would be a textual
presence check — the instrument class this repository has been bitten by twice.
So the suite IMPORTS THE REAL GATE and drives records through it:

    the real gate refuses a record past the bound                    asserted
    ...and does NOT refuse it one day earlier                        asserted  <- control
    this lane and the real gate cross at the SAME day, swept
      across offsets -2..+2 around the bound                         asserted

Plus the anti-brick control, measured a year out rather than a day past:
`assessTarget` produces exactly `["warn"]` per-push at +18, +54 and +365 days.

`enforceStaleness: true` puts arm A back on FAIL for a caller that IS a release
cut; it is exercised by the suite rather than left as an unreachable flag, which
is what keeps the two halves' arithmetic provably identical.

6. THE AUTO-RENEWAL TRIPWIRE — the durable half
--------------------------------------------------------------------------------
`drift-ci.yml` runs `npm run probe:support-windows` weekly and uploads the
rewritten record as an ARTIFACT; the release gate reads the COMMITTED file. That
distinction was the only thing making the 30-day bound mean anything, and
NOTHING PINNED IT. One `git commit` step in that workflow would have made the
bound renew itself, silently and forever.

RED-FIRST, against the real workflow text rather than a fixture:

    real drift-ci.yml + one appended commit/push step  ->  FLAGGED
        [{ path: "drift-ci.yml", mechanisms: ["`git commit`", "`git push`"] }]
    real drift-ci.yml unmodified                       ->  not flagged   <- the control
    a workflow that commits but never runs the probe   ->  not flagged   <- the conjunction is the rule
    `contents: write` on a probe-running workflow      ->  FLAGGED (before any commit step exists)
    the probe invoked as `tsx .../supportWindowsCli.ts` ->  FLAGGED (the obvious evasion)
    every real workflow in this repository             ->  no offender

Plus a scan-coverage control: the walk must see more than three real workflows
and exactly one that runs the probe, so an empty scan cannot pass as clean.
