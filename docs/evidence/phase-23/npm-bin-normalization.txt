--------------------------------------------------------------------------------
0. THE SYMPTOM
--------------------------------------------------------------------------------
The v1.6.0 publish log carried, twice:

    "bin[crabgic]" script name dist/bin.js was invalid and removed
    "bin[crabgic-supervisord]" script name dist/bin/supervisord.js was invalid and removed

Read literally, both binaries were dropped from the published package. They
were not. §1-§2 measure that; §3 reads the code that emits the sentence.

3. THE WARNING TEXT IS AN UPSTREAM MISLABEL — the mechanism, read not guessed
--------------------------------------------------------------------------------
npm 11.16.0, `@npmcli/package-json/lib/normalize.js` (path labelled above),
lines 65-72, verbatim:

        if (base !== binKey) {
          delete pkg.bin[binKey]
          changes?.push(`"bin[${binKey}]" was renamed to "bin[${base}]"`)
        }
        if (binTarget !== pkg.bin[binKey]) {
          changes?.push(`"bin[${base}]" script name ${binTarget} was invalid and removed`)
        }
        pkg.bin[base] = binTarget

Three things make the sentence wrong:
  (a) it fires when the NORMALIZED target differs from the written one — i.e.
      on every rewrite, not only on a removal;
  (b) `pkg.bin[base] = binTarget` on the very next line ASSIGNS the value the
      message just called removed;
  (c) it interpolates `binTarget`, the NEW value, as the thing that "was
      invalid" — which is exactly why the log said `dist/bin.js` (already
      stripped) while the manifest said `./dist/bin.js`. That mismatch is the
      tell.

The rewrite itself, same file, lines 127-134:

    function unixifyPath (ref) {
      return ref.replace(/\\|:/g, '/')
    }

    function secureAndUnixifyPath (ref) {
      const secured = unixifyPath(path.join('.', path.join('/', unixifyPath(ref))))
      return secured.startsWith('./') ? '' : secured
    }

The one genuine removal case is `secureAndUnixifyPath(ref) === ''` (npm's
`if (!binTarget) { delete ... }` a few lines above). Neither of this package's
targets is that case.

6. THE ASSERTION THAT WAS ADDED — and the one that was deliberately NOT
--------------------------------------------------------------------------------
NOT added: `expect(manifest.bin.crabgic).toBe("dist/bin.js")`. That is a
tautology over a literal one line away — vacuity pattern #1,
`docs/verification-playbook.md:75-76`. It would go green the moment it was
written and would measure nothing.

Added instead, in `scripts/check-published-tarball.mjs`: **every declared `bin`
target must survive npm's own normalizer unchanged**, i.e.
`secureAndUnixifyPath(target) === target` for every entry. That catches the
same class under a DIFFERENT key added later, and catches the four other shapes
npm rewrites (`/abs`, `../`, `a/../b`, `a:b`, backslashes) which a `./`-specific
check would not.

`secureAndUnixifyPath` is transcribed from the npm source quoted in §3, with
one deliberate divergence recorded in its own doc comment: `posix.join` instead
of the platform `path.join`.

--------------------------------------------------------------------------------
10. WHAT IS AND IS NOT CLAIMED
--------------------------------------------------------------------------------
CLAIMED: nothing was ever removed from the published package; the warning is an
upstream mislabel; the manifest now declares the form npm stores, so the
sentence cannot recur for these two keys; and a NEW key declaring a
normalizer-rewritten target reddens a per-push test.

NOT CLAIMED: that the warning is reproducible locally. `npm pack --dry-run` and
`npm publish --dry-run` at npm 11.16.0 emit no such line here — it surfaces on
the real publish path in CI, which this pass did not and must not run. The
mechanism in §3 is read from source rather than reproduced, and that is stated
rather than papered over.

NOT CLAIMED: any behavioural difference between the two forms. §1, §2 and the
`check:install-smoke` run in §9 all say there is none. This fix buys a legible
publish log, which is the only channel on which a REAL removal would ever be
noticed — that is the whole of its value, and it is defence of an instrument,
not of the program.

NO DEFECT RECORD IS OWED. Nothing in this repository was broken. The npm
wording bug is upstream and is recorded here rather than in this repo's
claim-space.
